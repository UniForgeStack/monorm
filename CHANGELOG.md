# Changelog

All notable changes are listed here, in the [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) format.

## [Unreleased]

- Admin: edit in the list. `list.editable` (Python) and `list: { editable }` (TypeScript) name the columns that staff edit in the cells of the list. The new route `PATCH {prefix}/resources/{name}` with `{"rows": [{"key", "set", "loaded"}]}` saves up to 200 rows in one transaction: `200` with the changed fields of each key, `400` and `409` with the problems by row index, `403` and `404`. Each rule of the form still applies (permission, `queryset`, `can=`, field permissions, `loaded` and the guard fields). A host behavior or service runs once for each changed row in one transaction (`update_rows`). The resource metadata has `editable`, the list has the save bar, and the build refuses a name that is not an editable column of the list, and a guard field that is not a list column. Breaking: none.
- Composed models: `delete()` through any level model of a model without soft delete removes every level row of the matched rows (one `DELETE` on the root row, the level keys cascade), as through the root and as Django does. Before, a child model removed only its own level. A model with soft delete keeps its soft delete. Breaking: code that relied on `delete()` through a child model to keep the parent or sibling rows must delete the child level with raw SQL; a test that expected one level to stay must change. The `DELETE` on the root row needs `ON DELETE CASCADE` on each level key: a composition over tables made by hand or by Django must add it first, or a `delete()` through a child model fails with a foreign key error.
- Composed models: `hard_delete()` through any level model, in the instance and the query-set form, removes every level row of the matched rows (sibling children too), as through the root and as Django does by default. Before, a child model removed only its own level. In database mode a live row still needs the soft delete first. Breaking: code that relied on `hard_delete()` through a child model to keep the parent rows must delete the child level with raw SQL.
- Field adapters: `insert_many(copy=True)` (`insertMany(..., {copy: true})`) now prepares pending values before the `COPY` (no `batch_size`, no `on_conflict`). `add()` and `set()` on a many-to-many set run no `prepare` when every link already exists. `FieldAdapter.validate` must also accept a stored value.
- History: versions mode. `@@history.versions(of:, scope:)` makes a user model the numbered version table of an aggregate, with `register(generate, restore)`, `record` (hash dedupe, a numbering lock on PostgreSQL), `version_at`, `timeline(diff)` and `restore` (a `restore` version with `restored_from`), in Python and TypeScript (`history(Model)`). The manifest has the new attribute `history.versions` and one logical pass `monorm.history.models`; the schema contract stays 5.3. [History](docs/extensions/history.md#versions-mode-historyversions) has the details.
- `pull` reads history and timestamps back. `pull` on SQLite now reads triggers that MonOrm wrote as `@@trigger(..., body: ...)`; another trigger stays a `// gap:` line. The extension manifest has a new `[[object_claims]]` table (generic, matched by name), so a database with the tables and triggers of `@@history.track`, `@@history.versions` and `@@timestamps.updated_at(mode: database)` pulls back as those attributes, not as event models, triggers and functions, and with no drift on PostgreSQL and SQLite. A name that the database cannot show (`row`, `label`, `when`, `fields`, `exclude`, `scope`, `upsert`, a partial `events` list, a composed model, a truncated name) falls back to the plain pull. A partial `events` list falls back with no gap line, and the `scope` keys of a version model come back as plain fields. The schema contract stays 5.3.
- `@db.Timestamp` on PostgreSQL: every write and filter binds the UTC value typed `timestamp`, so the session `TimeZone` no longer shifts the stored wall clock.
- Composed models: column roles and bulk inserts. `@@timestamps.updated_at`, `@@soft_delete.deleted_at` and `@@locking.version` now work on the root of a composed (multi-table) model, in database and application mode; before, the schema refused them anywhere in the ownership chain. Roles live on the root: a role on a level below it is a schema error that names the root. A change on any level bumps the root's `updated_at` and its version; a soft delete updates only the root; `hard_delete()` through any level model removes every level (in database mode a live row needs a second call); reads hide soft-deleted rows through the root; the soft-delete cascade reaches composed children. In database mode each level table gets an `AFTER UPDATE` touch trigger `updated_at_<column>_root` (skippable with `skip_triggers("timestamps")`). A scope on a composed root now loads. On PostgreSQL, `insert_many` on a composed model takes the keys in one statement and runs one multi-row `INSERT` for each level (L + 2 statements, not N × L); the new `attach_many` (TypeScript `attachMany`) does the same for existing parents. SQLite stays row by row. No IR or manifest change; the schema contract stays 5.3. Breaking: a composed model whose root has these roles now loads (a test that expected the error must change).
- Test isolation: `isolated(db=None, mode="rollback"|"truncate")` in `monorm.testing` (a decorator, a context manager, the `monorm_db` fixture, the `monorm` mark and the `monorm_autouse` option) and `isolated(fn, { db?, mode? })` in `monorm/testing`. `rollback` runs the test in a transaction that rolls back (nested transactions are savepoints, `on_commit` callbacks are dropped, `run_on_commit()` / `runOnCommit()` runs them); `truncate` empties every table and restarts identities. Parallel sibling savepoints under `rollback` raise `QueryError` with a hint to use `truncate`. The plugin needs `pytest-asyncio>=1.1`. New [Django coexistence](docs/guides/django-coexistence.md) guide. The schema contract does not change.
- Admin: base path and cookie scope. `base_path` (`[admin]` in `monorm.toml`, the `base_path` option of the Python `Admin`, `basePath` in TypeScript; default `/admin`) puts the UI, the API and every URL that the server builds under one path. The session and CSRF cookies get `Path=<base_path>/`, so two admins on one host keep separate sessions. In serve mode, a `base_path` in `monorm.toml` replaces the option of the object. The default API prefix is `<base_path>/api`. Breaking: an explicit `prefix` must sit under the base path, so `prefix = "/api"` or an empty prefix is now a build error (`admin.check()` reports it), and its first segment below the base path cannot be `-`, `assets`, `shared`, `index.html` or a resource name. Breaking: `Admin.prefix` (Python and TypeScript) is `None` / `undefined` unless you set it, and `DEFAULT_PREFIX` is removed from both bindings.
- History: the built-in `history` extension, track mode. `@@history.track(model:, events:, row:, label:, when:, fields:, exclude:, scope:)` adds an event model (`<Model>Event`, table `<table>_events`) and row triggers that write one JSON event for each insert, update and delete, on PostgreSQL and SQLite. `Model.history` and `row.history` (Python), `row.history` (TypeScript) give `timeline` (with `diff`), `at`, `event`, `backfill`, `restore` and `purge`. The core has a canonical JSON hash and a JSON object diff (`json_diff`, `canonicalHash`). The extension manifest has new `extension_records` and `added_triggers` records, so the schema contract is 5.3; an IR with `extension_records` is stamped 5.3, so an older engine refuses it with the version error. [History](docs/extensions/history.md) has the details.
- New `Bytes` scalar: `bytea` on PostgreSQL, `BLOB` on SQLite, `bytes` in Python, `Uint8Array` in TypeScript, base64 in JSON. It takes `=`, `!=`, `IN`, `NOT IN` and null checks; an order, a range, `LIKE` and an aggregate other than `count` raise `QueryError`. `pull` reads `bytea` and `BLOB` as `Bytes`; `String @db.ByteA` warns as deprecated. The IR has `ColType::Bytes`, so the schema contract is 5.3. The built-in `proto` extension adds `@proto.message("pkg.Msg")` on a `Bytes` field: the model types the field as your protobuf class (Google protobuf, protobuf-es v2, ts-proto, protobufjs or a registered `proto_codec`), the package map is in the settings file, and a query takes `IS NULL` and `IS NOT NULL` only. [Protobuf fields](docs/extensions/proto.md) has the rest.
- Soft delete: `pull` reads a soft-delete rule as `@@soft_delete.deleted_at("<column>", rule: "<rule name>")` (the guitars `ON DELETE DO INSTEAD UPDATE` shape and the plain shape; the new `rule:` argument needs `mode: "database"`), and `baseline` then `makemigrations` writes a move migration that drops the rule (`DROP RULE IF EXISTS`, before the trigger statements, in one transaction) and creates the monorm triggers. A rule of another shape, or a rule that is turned off, stays a `// gap:` line and is never dropped. The drop is `DROP RULE IF EXISTS`, so the move also runs on a new database. `rule:` is an error on SQLite. The extension manifest has a new `[[rule_claims]]` table and the IR has `TriggerIr.replaces_rule`, so the schema contract is 5.3 (an older host cannot read it). After the move, the setting `rules.hard_deletion` has no effect and a second `DELETE` of a soft-deleted row deletes it. The `down` of the move migration warns and does not recreate the rule. [Schema extensions](docs/extensions/schema-extensions.md#moving-from-guitars) has the steps.
- Soft delete: a lost cascade is a schema error. A model with `@@soft_delete.deleted_at` that a child reaches with `onDelete: Cascade` (a foreign key), where the child has no soft delete, now fails the schema load, in database and application mode, through any number of levels and through proxy and storage owner tables. Before, a soft delete of the parent kept the child rows without a warning. The error names the parent, the child, the relation and the two fixes. Fix one of two ways: add `@@soft_delete.deleted_at` to the child, or opt out on the relation field with the new `@soft_delete.keep_child_rows` (no argument), which keeps today's behavior: the child keeps its rows on a soft delete. The soft-delete manifest has a new field attribute, so its `schema_contract` is 5.3. Breaking: a schema that this check refuses needs one of the two fixes before an upgrade.
- Scope in the database: row-level security from `@@scope.by` (PostgreSQL). The migration enables and forces RLS on the table and creates the policy `monorm_scope` (the column equals `scope.<key>`, or the key is open in `monorm.bypass` and the role is in `bypass_roles`) and the insert trigger `monorm_scope_fill`. The datasource list `exempt_roles` gives each role a read-only policy. A level table of a composed model gets a policy that looks the row up in its direct parent (the compile step refuses `@@scope.by` in a composition chain today). New command `monorm audit`: exit 1 when the RLS flags or policies differ from the schema; it warns when the role is a superuser or has `BYPASSRLS`, and `migrate` warns the same for a schema with RLS. Both warn about a role of `bypass_roles` or `exempt_roles` that the database lacks. The core has a generic RLS IR (table flags and policies) with diff, SQL and introspection; `drift` and `pull` read them (`pull` lists policies as `// gap:` lines). The scope extension publishes its keys, so the ORM sets `scope.<key>` from the `scope()` context (a `scope=` option on one call is not sent). The schema contract stays 5.3. Breaking: a table with `@@scope.by` refuses raw SQL that carries no `scope.<key>` setting, for any role that is not a superuser or `BYPASSRLS`. [Scope](docs/extensions/scope.md) has the move from guitars.
- Scope runtime: one scope for the app and the database. `monorm.scope(shop=1, user=7)` (TypeScript `scope({ shop: 1 }, fn)`) sets values for the application. On PostgreSQL, a key that a policy reads is also set as the transaction-local setting `scope.<key>`. The settings travel with the first statement of the transaction (about 1.1 round trips warm, 2.1 cold; measured, 40 ms delay proxy). The built-in `scope` extension adds `@@scope.by(shop: shop_id)`: a read filter, the insert fill and a write check. New errors `ScopeMissing` and `ScopeMismatch` (both `QueryError`). `unscoped(*keys)` opens keys and sets `monorm.bypass`. `skip_triggers(*extensions)` sets `monorm.skip`; the timestamps trigger skips only for a role in `bypass_roles` of the `datasource` block (empty by default). `QueryEvent.settings` shows the settings in the trace. The extension manifest has open named arguments and a scoped-field record, so the schema contract is 5.3; an older host cannot read a 5.3 manifest (it fails with a parse error, not a version error). An older `generate` or `pull` that writes the IR again drops `bypass_roles` and `skippable`. Breaking: `db.tenant()` is removed from Python, TypeScript and Rust, and `bind_request(tenant=)` / `bindRequest({ tenant })` too. It set `app.tenant`; use `scope(<key>=...)` for the application. The generated policies read `scope.<key>`, not `app.tenant`: drop a hand-written policy that reads `app.tenant`. TypeScript `bindRequest` throws `TypeError` for a `tenant` option; Python raises `TypeError`. The admin sets its row scope through the same scope context.
- Soft delete: the check for a default filter that only repeats `deleted is null` now reads the read defaults of every other extension on the model, so it also rejects a filter that the model inherits from a parent (`@@query.parent`). Before, only a filter written on the model itself was rejected. A schema with such an inherited filter that compiled now fails, with the position of the parent declaration. To keep the parent filter off the child, override it on the child by name (`@@query.filter("<name>", "none")`). The check runs as a new validation pass, `monorm.soft-delete.check`; the error text for an own filter is the same.
- Auth: the opt-in `breached` password rule. Add `{ rule = "breached" }` to `[auth] password_rules` to refuse a password that is in a known data breach. It asks a Pwned Passwords range API and sends only the first 5 hex characters of the SHA-1, with `Add-Padding: true`. Options: `threshold` (default `0`), `host`, `timeout` (seconds, default `2`) and `fail` (`"open"` by default, or `"closed"`). The error is `password_breached` `{count}`; with `fail = "closed"` an unfinished check gives `password_check_unavailable`. The rule is not in the default list, and Rust makes no network call: Python and TypeScript run the request.
- Default filters are schema expressions. `@@query.filter("tenant", shop_id == scope.shop)` and `@@query.defaults(filter: active == true)` take an expression in the native syntax (`&`, `|`, `~`, `.startswith()`, `.between()`, `.in_()`). The core checks its types when the schema loads. The extension manifest has a new argument kind `expression`, so the schema contract is 5.2. The string form is deprecated: it still works, with a warning that shows the expression to write. A string filter is now type-checked too, which can reject a filter that the database accepted before. `monorm fmt --native` rewrites the strings. `"none"` stays a string. An older host cannot read a 5.2 manifest, and an older engine refuses an IR with a new filter shape.
- Auth: password rules. `validate_password` / `validatePassword` checks a new password against `[auth] password_rules` (`passwordRules` in `package.json`): the default list is `min_length` 8, `common` (a bundled list of 10,001 passwords, SecLists, MIT), `numeric` and `user_similarity` (the `quick_ratio` of Django). The built-in rules run in one Rust function, so both languages give the same result; custom rules are `module:attr` and may be async. An error is `{code, message, params}`. `create_user` and `set_password` do not check. Breaking: the admin password change refuses a new password that breaks a rule, with `400` `WeakPassword`; a password shorter than 8 characters no longer works there unless you set `password_rules`.
- `pgbouncer=true` URL flag (PostgreSQL). Every query, write, raw read, prepared call and `copy_in` runs as an unnamed statement, so a transaction pooler that moves a connection to another server cannot break a named statement (`26000`, `42P05`). The engine reads the enum and composite types once for each pool connection (list every type in the schema), then sends `DEALLOCATE ALL`. A session lock and a no-transaction migration fail with an error before any SQL. A `sqlite:` URL refuses the flag. Not needed on PgBouncer 1.24 or later with the default `max_prepared_statements`. A CI job runs the tests through PgBouncer in transaction mode.
- Online index and constraint migrations (PostgreSQL). With `migrations.online = true` (`[migrations] online = true` in the settings file; Python `Migrations(..., online=True)`; TypeScript `new Migrations(dir, schema, { online: true })`), `makemigrations` writes `CREATE INDEX CONCURRENTLY` and `DROP INDEX CONCURRENTLY` for an existing table in no-transaction folders, and adds a foreign key or check as `NOT VALID` with a `VALIDATE CONSTRAINT` folder after it. Each folder has its own snapshot. New tables and unique indexes stay in the main folder. The default is `false`, and the output with the setting off, or on SQLite, does not change. `Step.transaction` is `false` for a concurrent step. Each folder name has the migration label and a suffix (`_drop_<index>`, `_index_<index>`, `_validate`), so `--name` is in every folder name; an index or foreign key of a partitioned table stays in the main folder, and a check of one is added `NOT VALID`. Breaking: `Migrations.make()` returns the list of the folders it wrote (an empty list when nothing changed), not one `Migration` or `None`/`null`.
- `select(...).union(other)` and `.union_all(other)` (TypeScript: `unionAll`) in Python and TypeScript: the rows of two `select()` queries in one SQL statement (`UNION` or `UNION ALL`, on PostgreSQL and SQLite). The result is a `CompoundSelect` with a final `order_by()` by output name, `limit()`, `offset()`, slices, `all()`, `require()`, `first()`, `get()`, `count()`, `exists()`, `scalar()`, `scalars()`, `sql()`, `inspect()` and `explain()`. Both sides need the same output names, order and types; only nullability may differ, and `String` and `Text` count as one type. A side keeps its own filters, order and slice. A side cannot have a CTE, `param()`, `outer()`, a model, a nested or JSON column, a write or a lock. `INTERSECT`, `EXCEPT` and a model query-set union are not part of it.
- SQL views and materialized views. A `view Name { ... }` block holds a read-only model; its `SELECT` is in `views/<db schema>/<Name>.sql` next to the schema file. `@@materialized` (PostgreSQL), `@@depends_on([Other])` and `@@index` on a materialized view. A migration creates, drops and recreates views (views drop first and return last); the snapshot version is now 5. A view refuses every write with `ReadOnlyModel`, and the generated types have no write inputs. `db.refresh(Model, concurrently=...)` runs `REFRESH MATERIALIZED VIEW`. `pull` and `drift` read views back. A view drop loses its grants and comment. SQLite has plain views only.
- No-transaction migrations (PostgreSQL). A migration folder whose `up.sql` starts with `-- monorm: no-transaction [create-index <name> | drop-index <name>]` runs without a transaction, so it can hold `CREATE INDEX CONCURRENTLY` or `DROP INDEX CONCURRENTLY`. One statement per folder. The runner holds the migration lock on a session of its own, drops an invalid index left by a failed build, and records the migration after the SQL. A folder with a data step, or any use on SQLite, is refused. A `down.sql` can carry the header too.
- `returning(*columns)` on every write (`insert`, `insert_many`, `update`, `update_many`, `delete`) in Python and TypeScript. With no columns a write returns the default selection (the read defaults, minus what `without_defaults()` bypasses). With columns it returns those columns plus the key and helper fields; every other field is `NotLoaded`. A multi-table (composed) model follows the same rules, and its read defaults apply. A relation in `returning()` and `load()` on a write raise `TypeError`: load relations with `monorm.of(rows).load(...)`. Breaking: `insert()` now returns the default selection, not every field, so a field that a read default hides is `NotLoaded` on the new instance, also when you set it; call `without_defaults()` first to get it. Breaking, TypeScript: `{ returning: true }` on `update`, `delete` and `updateMany` is removed (this is a beta, with no deprecation): use `.update(...).returning()`. `insert_many(..., copy=True)` still gives a count.
- Prepared reads are held in Rust. `prepare()` plans a read once and keeps the SQL text with a slot map: a call converts and binds, with no JSON parse and no planning, for `get`, `first`, `count`, `exists` and the plain call. Scope values are per-call: `scope=` (TypeScript `{ scope }`) on a call wins over the `scope()` context, and `prepare()` works with no scope active. `in_(param())` and `not_in(param())` take a list of any length (`= ANY` on PostgreSQL, `json_each` on SQLite). `param(name, type)` declares a type; a `CASE` of params only needs one. A shape that cannot become a slot raises at `prepare()`. PostgreSQL prefetch with a one-column key uses `= ANY($1)`. `scope` is a reserved `param()` name.
- Prepared writes. `.prepare()` on `insert`, `insert_many`, `update`, `update_many`, `delete` and an upsert (Python and TypeScript) keeps the statement in Rust, like a prepared read. `param("rows", fields=(...))` takes the rows of `insert_many` and `update_many` (primary key first); `None`/`null` in a set or insert value writes `NULL`, and in a filter raises; a row with a missing or extra key raises before any SQL. `returning(cols)` is fixed at prepare; scope, hooks and the write guard run on each call. On PostgreSQL a prepared batch of 32 rows or more binds one array for each column (`UNNEST`). A hook that gives a value at plan time, and a multi-table `update` or `delete`, raise at `prepare()`.
- Destructive-change gate. `makemigrations` writes a `-- monorm: destructive <kind> <table>[.<column>]` line above each step that drops a table, drops a column, or changes a column type so that values can be lost; `Step.destructive` says the same in Python and TypeScript plans. Breaking: `migrate` and `rollback` refuse such a migration when the marked table has rows, unless you pass `--allow-destructive` (Python `allow_destructive=True`, TypeScript `{ allowDestructive: true }`). A missing or empty table passes, and a migration made before this change has no markers.
- Write guard: `update()` and `delete()` on a query set with no caller filter (`filter()`, `exclude()`, a related set) raise `UnfilteredWriteError` before any SQL, in Python and TypeScript. A filter that is always true (`and_()` of no conditions) does not count as a caller filter. Call `.all()` first (`Post.objects.all().delete()`) to write every row. Or open the database with `connect(url, allow_unfiltered_writes=True)` (TypeScript: `{ allowUnfilteredWrites: true }`). `hard_delete()` is guarded too. Instance writes, `insert()`, `update_many()` and raw SQL are not guarded. Breaking: code that updates or deletes every row without a filter needs `.all()`.
- TypeScript: `QuerySet.all()` and `Select.all()` return a lazy copy with an empty result cache, as in Python. Before, `all()` ran the query at once. Breaking: `await qs.all()` still works, but `qs.all()` is not a `Promise`, so `transaction(() => qs.all())` no longer type-checks: write `transaction(async () => qs.all())`.
- Transaction options: `db.transaction(isolation=..., timeout=...)` in Python and `db.transaction(fn, { isolation, timeout })` in TypeScript. `isolation` is `read_committed`, `repeatable_read` or `serializable`; SQLite runs every level as serializable. `timeout` is one client-side deadline of the Rust engine for the whole outermost transaction: it starts before the wait for a connection and covers setup, statements, idle time and commit. The engine cancels the work, rolls back and raises the new `TransactionTimeoutError` (a `DatabaseError`) with `outcome` `rolled_back` or `unknown` (a sent `COMMIT` that did not finish). A nested call rejects explicit options with `QueryError`.
- `monorm.toml` is the first settings file of every `monorm` command (`schema`, `migrations`, `query_sets`, `model_methods`). `[tool.monorm]` in `pyproject.toml` and the `"monorm"` key of `package.json` stay as the fallback, in that order; the first file that holds settings wins and the files do not merge. On Node, `[tool.monorm]` in `pyproject.toml` now wins over the `"monorm"` key of `package.json`; the Node host used to read `package.json` first. A settings file that does not parse is an error that names the file: `monorm` used to skip a broken `pyproject.toml` or `package.json`. A file after the winner is not read. A wrong key type, or the key spelling of another file format (`querySets` in a TOML file, `query_sets` in `package.json`), is an error that names the file and the key. The `query_sets` and `model_methods` tables come from the winning file for every language, so a project that keeps Python query sets in `pyproject.toml` and TypeScript query sets in `package.json` moves them to one `monorm.toml` per language directory. `monorm init` writes a `monorm.toml`.
- `ValidationError` in Python and TypeScript: messages per field path (`address.city`, `lines.2.qty`) and messages with no field (`non_field_messages`, `nonFieldMessages` in TypeScript). A dot in a field name is not escaped. It crosses the binding as a typed error, and Rust code reads it as `monorm_engine::ValidationError`.
- `monorm init [dir]` starts a Python or TypeScript project: it asks for the language, the tool, the database and the built-in extensions, and flags answer each question. `uvx monorm init`, `python -m monorm init`, `npx monorm init` and `npm create monorm` run the same code. The PyPI package now has a `monorm` console script, and `create-monorm` depends on `@ufstack/monorm`.
- Auth: `sync_permissions` / `syncPermissions` takes the permission names (`<label>.<codename>`) and creates the absent ones in one bulk insert. It deletes nothing. `model_permission_names` / `modelPermissionNames` gives the Django-style per-model names. Breaking: the call `sync_permissions([Post], "blog")` becomes `sync_permissions(model_permission_names([Post], "blog"))`.

- Linux arm64: a `manylinux_2_28_aarch64` wheel on PyPI and a `linux-arm64` addon in the npm package. The two Linux platforms need glibc 2.28 or newer. Outside extension packages ship a `linux-arm64` library in a `<platform>/` directory, and their wheel tag has `manylinux_2_28_aarch64`.

## [0.1.1] - 2026-10-30

- The npm package is `@ufstack/monorm`, because npm rejected the name `monorm`. Install it under the alias `monorm`: `npm install monorm@npm:@ufstack/monorm`. Imports stay `monorm`.

## [0.1.0] - 2026-10-30

- Renamed from `orm` to `monorm`. The CLI is `monorm` and the Python module is `monorm`.
- Async Python and TypeScript APIs on one Rust core: queries, relation loading with `load()`, transactions, locks and protected writes.
- One Prisma-syntax schema (`schema.prisma`) for both languages, with generated typed models and migrations.
- PostgreSQL and SQLite.
- Query builders for `select()`, subqueries, windows and CTEs, plus cursor pagination and an N+1 finder.
- OpenTelemetry hooks.
- Build-time extensions: proxy models, query defaults, model composition, file storage, generic relations, timestamps, soft delete, optimistic locking and inherit.
- One package per registry: PyPI `monorm` (12 platform wheels), npm `monorm` (one tarball for 3 platforms) and the crate `monorm` (the contracts library). Each of the first two holds the engine, both databases, the CLI, the nine built-in extensions and the `monorm-auth` app. Outside extensions install next to it, for Python and npm.
- `MONORM_PROFILE`, the `monorm[...]` extras, the native-profile packages and the per-extension packages do not exist.
- A typed read client for Rust in `languages/rust/` (not published).
- Benchmarks against Django and Prisma in `bench/compare/`, recorded in `bench/RESULTS.md`.
