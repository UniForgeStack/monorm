# MonOrm internal benchmark: report (2026-10-30)

Two sets of runs on one cloud VM, each with 3 runs on PostgreSQL and 3 on SQLite. All 12 runs are marked **valid** in `run.json`.

- **Main set: `--rounds 45`**, in `2026-10-30-6332db55-r45-<backend>-<n>/`. All the tables below are from this set, unless they say otherwise.
- **First set: `--rounds 15`** (the default), in `2026-10-30-35cde71d-<backend>-<n>/`. It is kept for comparison; its layer tables are at the end.

The 15-round set was noisy on PostgreSQL, so the same VM was measured again with 3× the rounds.
The 45-round set has a smaller spread between runs: 48 of 104 case/path rows above 10%, down from 63 (PostgreSQL 27/52, down from 41/52; SQLite 21/52, down from 22/52).

Every number is **measured**. Each is the median of the timed batches in µs per operation, as written by the benchmark, and then the median over 3 runs.
Nothing is estimated or extrapolated.

## Source and changes

- Repository `https://github.com/UniForgeStack/monorm`, branch `main`.
  - The 15-round set measured `35cde71d` (`v0.1.1-2-g35cde71d`).
  - The 45-round set measured `6332db55`, the main branch some hours later.
  - The three commits between them only add the `create-monorm` package, a guide and release-script metadata. They change nothing in the engine, the bindings or `bench/internal/`.
  - The 45-round set therefore reused the release build in `bench/internal/build/` with `--skip-build`. That build was made from `35cde71d`, whose sources are the same for everything the benchmark runs.
- **One code change**, committed with these results: it deletes line 48 of `bench/internal/run.sh`, `mkdir -p "$BUILD" "$OUT"`.
  - That line ran before `OUT` got its default value, so every run without `--out` failed at once with `mkdir: cannot create directory '': No such file or directory`.
  - Line 60 already creates the directory once `OUT` is set.
  - `scripts/tests/test_internal_bench.py` did not catch it because it always passes `--out`.
  - After the change, the smoke test (`MONORM_BENCH_SMOKE=1 python -m unittest scripts/tests/test_internal_bench.py`) passes, and `bench/internal/run.sh --quick` without `--out` succeeds.
- The default result name `<date>-<commit>-<backend>` has no run number, so 3 runs on the same day would overwrite each other.
  The runs passed `--out` with an absolute path and a run number.
- The release build changes `bench/internal/rust/Cargo.lock` (1 line) and `languages/js/package-lock.json` (24 lines removed), through its own `cargo build` and `npm install`. Those changes are not committed.

## Layers per backend and language (45 rounds)

The layers are computed exactly as in `report.py`:
- builder = unprepared − prepared (for the insert: unprepared − direct IR)
- value binding = prepared − direct IR
- hop + instances = direct IR − engine only
- engine = engine only − driver only
- driver = driver only

Each run's layers are computed first. The table shows the median of the 3 run values, with their min–max in brackets.
"unprepared total" is the median of the 3 unprepared medians.

## The 3 largest layers overall (45 rounds)

Ranked by each layer's largest median value over all cases, languages and backends:

| rank | layer | largest value (µs/op, measured, median of 3, min–max) | case | language | backend |
|---|---|---|---|---|---|
| 1 | driver | 2,911.5 (2,862.2–3,197.6) | read_1000 | TypeScript on Node (`pg`) | PostgreSQL |
| 2 | hop + instances | 1,474.7 (1,406.7–1,561.4) | read_1000 | TypeScript on Node | PostgreSQL |
| 3 | builder | 266.1 (244.9–288.9) | read_1000 | Python | SQLite |

- The engine layer's largest value is 200.2 µs (PostgreSQL, Python, `filtered_count`). That value comes from the bimodal Rust row described below, so it is not a real engine cost.
- Leaving that out, the engine layer peaks at 157.2 µs (SQLite, Python, `insert_one`).
- Value binding peaks at 70.8 µs (PostgreSQL, Python, `prefetch_posts`).
- The 15-round set gives the same top 3, in the same cases and languages (3,085.5 / 1,501.0 / 332.9 µs).

What this says:
- **Hop + instances is the largest MonOrm layer in every case, language and backend,** except PostgreSQL `filtered_count`, where the engine-only row is off (see below).
  It is largest for `read_1000`, where it builds 1,000 model instances: about 620–880 µs on SQLite and 770–1,475 µs on PostgreSQL.
- **Hop + instances costs more in Node than in Python for `read_1000`** (1,475 vs 767 µs on PostgreSQL, 877 vs 619 µs on SQLite). It costs less in Node for the small cases (`pk_get`: 65–77 µs in Node vs 168–175 µs in Python).
- **The builder costs more in Python than in Node** in most cases. On SQLite it is 35–266 µs in Python vs 14–96 µs in Node, and on PostgreSQL 85–253 µs in Python vs 43–220 µs in Node.
  For `pk_get` in Python the builder is 94–175 µs, a fifth to a third of the call.
- Value binding is small: at most ~70 µs, and often inside the noise.

## Anything odd

**The PostgreSQL `filtered_count` engine-only row is bimodal.**
- The Rust row measured 198.3, 419.8 and 415.0 µs in the 3 runs of the 45-round set. In runs 2 and 3 *every* one of the 45 samples (335–631 µs) is above run 1's maximum (255 µs).
- In the 15-round set it measured 265, 229 and 214 µs.
- The Python and Node direct paths run the same query through the same engine, and they did not jump.

As a result, hop + instances for this case comes out negative (Node −67 µs, Python 23 µs with a range down to −56 µs) and the engine layer comes out large (+132 to +200 µs).
**These two layers are not valid for PostgreSQL `filtered_count` in the 45-round set.** The 15-round set shows plausible values for them.

The cause is not known. One candidate is that the Rust runner runs last, after the Python and Node insert cases, on a `posts` table that autovacuum and autoanalyze visited during the session.
A separate test (9,000 rows inserted and deleted in `posts`) slowed the same `COUNT(*)` inside PostgreSQL by only about 20 µs. Dead tuples alone do not explain a 200 µs jump.
A possible change for the benchmark: run `VACUUM ANALYZE` on the tables before each runner's timing.

**Negative layers (45 rounds).** Each line gives the median of 3 and the 3 run values:

- postgresql Python pk_get engine: median -18.9 µs (runs -23.6, -18.9, -18.3)
- postgresql Python filter_order_50 engine: median -20.6 µs (runs -51.0, -1.9, -20.6)

- postgresql TypeScript on Node pk_get engine: median -38.9 µs (runs -39.4, -38.9, -37.1)

- The **engine layer on PostgreSQL is negative for almost every case**, by up to −749 µs (Python) and −1,547 µs (Node) for `read_1000`.
  This is not timing noise.
  The engine-only row is the full Rust path (parse, plan, run and read every cell, with the Rust PostgreSQL driver), and it is faster than the raw `psycopg` or `pg` driver row alone.
  The README warns that the engine layer "also holds the difference between the two drivers".
  On PostgreSQL that difference is bigger than the engine's own cost, so **this layer cannot show the engine's cost on PostgreSQL**.
  On SQLite the engine layer is positive (about 30–160 µs) except for `read_1000`, where the Rust row is again faster than the language's own `sqlite3`/`node:sqlite` driver.
- The other negative values in value binding and hop + instances are noise, as the README says: the two paths are closer than the run can tell apart. The exception is PostgreSQL `filtered_count` (above).

**Skipped and n/a rows.** No row was skipped in any of the 12 runs: both raw drivers (`psycopg`, `pg`, Python `sqlite3`, `node:sqlite`) and the Rust engine row ran each time.
The only n/a is the prepared path of `insert_one`, in both languages and on both backends, with the reason "a write has no IR to prepare" (as designed).

**Checks.** Every case in every result file has `"checked": true`: all paths returned the same result before the timing.

**Errors and warnings.**
- The `run.sh` bug above, fixed in the commit that adds these results.
- The first attempt after the fix failed with `_native.DatabaseError: error connecting to server`. The container had restarted during the build and PostgreSQL was down. This is an environment problem, not a MonOrm bug.
  The release build had completed, so the valid runs used it with `--skip-build`.
- The second attempt passed a relative `--out` path. `run.sh` starts Node from `bench/internal/js/`, so the Node JSON landed under `bench/internal/js/bench/internal/results/` and each `summary.md` said "No result file" for TypeScript.
  That attempt was discarded and all 6 runs were repeated with absolute paths.
  Small hardening idea for `run.sh`: make `OUT` absolute before use.
- Node prints `ExperimentalWarning: SQLite is an experimental feature` on the SQLite runs (Node 22's `node:sqlite`). It is harmless.
