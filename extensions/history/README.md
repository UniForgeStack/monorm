# history

`@@history.track` writes one event row for each insert, update and delete of a model, with database triggers.
`@@history.versions(of:, scope:)` turns a model into the version table of an aggregate.
`track` takes `model`, `events`, `row`, `label`, `when`, `fields`, `exclude` and `scope`.

## Install

The extension ships inside the one `monorm` package.
Python: `pip install monorm`.
TypeScript: `npm install monorm@npm:@ufstack/monorm`, then `import { history } from "monorm/extensions/history"` for the class-level entry.
There is no separate wheel or npm package.

## Smallest example

```prisma
model Post {
  id    Int    @id @default(autoincrement())
  title String
  body  String?
  @@history.track
}
```

```python
post = await Post.objects.insert(title="a")
await Post.objects.filter(Post.id == post.id).update(title="b")
timeline = await post.history.timeline(post, diff=True)   # [insert, update]; timeline[1].diff has the change
```

```ts
const post = await Post.objects.insert({ title: "a" });
await Post.objects.filter(Post.id.eq(post.id)).update({ title: "b" });
const timeline = await post.history.timeline(post, { diff: true });
```

## How it works

### Schema pass

* `monorm.history.models` (storage phase) runs after the proxy and composition passes, which run in the logical phase, so it sees the root of each model.
  For a tracker it adds the event model, `<Model>Event` by default, with the table `<root table>_events`.
  For a version model it adds the version columns.
* `monorm.history.triggers` (late behavior phase) runs after `monorm.timestamps.prepare` (behavior phase) and adds the row triggers.
* Checks (each error names the attribute and the place):
  * A composed model fails: `track each part model, or use versions mode`.
  * `when` needs `update` in `events`. `events`, `fields` and `exclude` name known values and no duplicates.
  * Two trackers of one table with the same trigger suffix fail: name the event model with `model: "Other"`.
  * The trigger function name must have at most 63 characters.
  * SQLite takes at most 500 tracked fields in one event.
  * `@@history.versions` needs a model with its own table and a single-field primary key with a database default.
    `of` must not name the primary key. A model cannot have both `track` and `versions`.

### SQL

The sample is the PostgreSQL migration of the `Post` model above:

```sql
CREATE TABLE "post_events" (
    "id" bigint GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    "row_id" integer NOT NULL, "label" varchar NOT NULL, "data" jsonb NOT NULL,
    "created_at" timestamp with time zone DEFAULT now() NOT NULL, "xact_id" bigint,
    CONSTRAINT "post_events_pkey" PRIMARY KEY ("id")
);
CREATE INDEX "post_events_row_idx" ON "post_events" ("row_id", "id");
-- function post_h_events_upd(), shortened:
INSERT INTO "post_events" ("row_id", "label", "data", "xact_id") VALUES (NEW."id",
  CASE WHEN current_setting('monorm.history_restore', true) = 'post_events' THEN 'restore' ELSE 'update' END,
  jsonb_build_object('id', NEW."id", 'title', NEW."title", 'body', NEW."body"), pg_current_xact_id()::text::bigint);
CREATE TRIGGER "h_events_upd" AFTER UPDATE ON "post" FOR EACH ROW WHEN ((OLD."id", OLD."title", OLD."body") IS DISTINCT FROM (NEW."id", NEW."title", NEW."body")) EXECUTE FUNCTION "post_h_events_upd"();
```

* PostgreSQL: triggers `h_<suffix>_ins`, `h_<suffix>_upd` and `h_<suffix>_del`, and functions `<table>_h_<suffix>_ins|upd|del`.
  The suffix is `events` for the default model, and the snake-case name of a `model:` argument.
* SQLite: one trigger for each event kind, named `<table>_h_<suffix>_ins_trigger`, `..._upd_trigger` and `..._del_trigger`.
  It stores `NULL` in `xact_id` and in the scope columns.
* A `scope: [user]` tracker adds a `"user" varchar` column. The trigger fills it with `nullif(current_setting('scope.user', true), '')`.
* `@@history.versions(of: bundle_id, scope: [user])` adds these columns to the model:
  `version_number`, `snapshot jsonb`, `content_hash text`, `effective_at`, `change_type`, `restored_from`, `xact_id` and `"user"`.
  It also adds a `CHECK` on `change_type`, a foreign key `restored_from` with `ON DELETE SET NULL`, and the unique index `<table>_<of column>_version_key` on (`of`, `version_number`).

### Runtime hooks

* History event models are append-only. Updates and deletes raise `WriteProtected` in the ORM and on PostgreSQL. Purge uses `allow_writes()` and needs a role in `bypass_roles` on PostgreSQL. SQLite keeps the application rule.
* `restore` sets the transaction setting `monorm.history_restore` on PostgreSQL, so the trigger writes the label `restore`.
  SQLite cannot read a setting, so `restore` relabels its own events after the write.
* `skip_triggers("history")` skips the triggers for a role in `bypass_roles`, on PostgreSQL only.
* A version model needs `register(generate, restore)` once.
  `record` takes a transaction lock for the table and the entity on PostgreSQL.

### Crate and bindings

* The crate `monorm-history` builds the models, the triggers, the backfill SQL and the version insert SQL.
* `python/monorm_history` holds the API: `timeline`, `at`, `event`, `backfill`, `restore`, `purge`, and in versions mode `register`, `record`, `version_at`.
* `typescript/src` holds the same API in camel case, plus `history(Model)` for the class-level entry.

### Other extensions

* A tracker ignores an update that changes only a column that the timestamps extension owns.
* `scope: [key]` publishes the key (`behavior.published_scope_keys`), so `scope()` accepts it without a `@@scope.by` that uses it.
  The scope extension adds to the same list.
* A proxy and a composed model are tracked through their root table, or through each part model.

```
extensions/history/
  monorm-extension.toml
  src/lib.rs
  python/monorm_history/
  typescript/src/
  tests/fixtures/schema.prisma
  tests/public/{python.py,node.mjs}
```

Run `cargo test -q -p monorm-history` for the crate.
Run `python extensions/history/tests/public/python.py` and `(cd languages/js && node ../../extensions/history/tests/public/node.mjs)` for the public tests.
Set `ORM_TEST_DATABASE_URL` to run them on PostgreSQL too.
The behavior tests are `languages/python/tests/test_history.py` and `test_history_versions.py`, and `history.test.ts` and `history-versions.test.ts` in `languages/js/test/`.

## Limits

* A backfill on a large table runs as one statement.
* SQLite stamps `effective_at` with whole seconds.
* A `BigInt` above 2^53 loses precision in `data` in TypeScript, and `restore` refuses such an event.
* `pull` reads the event and version tables as plain models.
  On PostgreSQL it also writes the triggers as `@@trigger(...)` lines, and on SQLite it reports the triggers as a gap.
  It never writes a `@@history.*` attribute.
* Errors a user meets: `WriteProtected` on an update or delete of an event, `QueryError` from `skip_triggers("history")` on SQLite, and `ValueError` from `record` with the change type `restore`.
