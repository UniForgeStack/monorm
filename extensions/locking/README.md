# locking

`@@locking.version` adds an integer `version` column for optimistic locking.
Each write adds 1 to it, and a write of a loaded object fails with `VersionConflict` when the row has another version.
The attribute takes `name`, `upsert` and `map`.

## Install

The extension ships inside the one `monorm` package.
Python: `pip install monorm`.
TypeScript: `npm install monorm@npm:@ufstack/monorm`.
There is no separate wheel or npm package.

## Smallest example

```prisma
model Doc {
  id    Int    @id @default(autoincrement())
  title String
  @@locking.version
}
```

```python
doc = await Doc.objects.get(Doc.id == 1)
try:
    await doc.update(title="new")
except monorm.VersionConflict:
    await doc.load(reload=True)
```

```ts
const doc = await Doc.objects.get(Doc.id.eq(1));
try {
  await doc.update({ title: "new" });
} catch (e) {
  if (!(e instanceof VersionConflict)) throw e;
}
```

## How it works

### Schema pass

* `monorm.locking.fields` (declaration phase) adds the field before the logical passes, so a proxy copies it.
* `monorm.locking.prepare` (behavior phase) records the write assignment and the instance guard.
* `upsert` is `drop` (default) or `pick`: it decides whether the `DO UPDATE` list of an upsert holds the field.
* Errors: `` `<Model>` has more than one version field`` and `` `<view>`: proxy must keep the version field `<f>` ``.
* The field form fails like the one of timestamps: write the model attribute.

### SQL

The only change is the column. There is no trigger and no index.
The sample is the PostgreSQL migration of `Doc`:

```sql
CREATE TABLE "doc" (
    "id" integer GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    "title" varchar NOT NULL,
    "version" integer DEFAULT 0 NOT NULL,
    CONSTRAINT "doc_pkey" PRIMARY KEY ("id")
);
```

### Runtime hooks

* `behavior.write_assignments.locking`: each update, soft delete, `undelete` and upsert `DO UPDATE` sets `version = version + 1`, unless the write sets the field.
* `behavior.instance_guards`: an instance `update()` or `delete()` adds `AND version = <loaded>` to the `WHERE` clause.
* A bound write (`doc.qs().update()`, `monorm.of(docs).delete()`) matches the `(key, version)` pairs of the held objects.
  A conflict rolls the write back and changes no row.

### Crate and bindings

* The crate `monorm-locking` holds the schema passes.
* `python/monorm_locking` holds `LockingBoundQuerySet`, which does the pair match and raises `VersionConflict`.
  `LockingQuerySet` and `LockingInstance` have no members.
* `typescript/src` holds `lockingBoundQuerySet` and the same check.

### Other extensions

The cascade trigger of soft delete adds 1 to the `version` of a child that has locking.
Soft delete also adds 1 to the `version` of its own row.

## Layout

```
extensions/locking/
  monorm-extension.toml
  src/lib.rs
  python/monorm_locking/
  typescript/src/
```

There are no `tests/public`.
Run `cargo test -q -p monorm-locking` for the crate.
The behavior tests are `languages/python/tests/test_version_pairs.py` and `test_tracking.py`, and `languages/js/test/version-pairs.test.ts` and `tracking.test.ts`.

## Limits

* A query set `update()` does not check the version (as Rails `update_all`).
* An instance `hard_delete()` has no version check.
* An instance `update()` with an explicit version field raises `TypeError`.
* An instance without the version field loaded cannot write.
* A write that does not go through the ORM does not add 1: a trigger does not exist for this extension.
